## A. The primitives that exist today (trusted layer, per source)

### A1. Process supervision (loader/src/supervisor.ts)
- The loader is the container's main process (`docker/instance/Dockerfile` ENTRYPOINT: `tini -- node loader/dist/main.js`) and owns **one** child: `supervisor.ts:323` spawns `'node', [config.lifemodelEntry]` into singleton `child`/`startInFlight`/`state` fields (`:178` "an older child, already replaced" guard) — a second simultaneous child has no slot in the current design.
- Spawn carries `uid`/`gid` **only when `config.privileged`** (`supervisor.ts:165-174`; `config.ts:242` `privileged = process.getuid() === 0`), otherwise it is the loader's own identity. Defaults: `LIFEMODEL_UID/GID` env, default 1000 (`config.ts:200`).
- OS-spawn confirmation (`exec.ts SpawnedProcess.onSpawn`) is the only "it really runs" fact; uptime-only backoff reset; `LIFEMODEL_RESTART_EXIT_CODE = 75` (`supervisor.ts:46`) restarts; a panic-read blocks starts (`supervisor.ts:245,311`); stop is bounded (95 s drain wait vs 90 s drain, one overall `LIFEMODEL_STOP_BUDGET_MS` deadline; documented stop budget 110 s vs Docker `--stop-timeout 120` — `README.md:192,243`).
- No generation identity is carried by a start: every start runs the same `config.lifemodelEntry` path (`/var/lib/lifemodel/repo/dist/index.js`; `supervisor.ts:323`).

### A2. Filesystem authority (loader/src/state.ts, fs.ts, repo.ts, bootstrap.ts)
- Volume layout: `<volume>/loader/` root-only `0700` (`loader/src/state.ts:25` `LOADER_DIR_MODE`; the four files auth/panic/cli-token/state at `0600`, `:24`); `data/`'s directory is given to uid 1000 only when this start created it (`state.ts:118`), and the fresh seed clone is given whole once (`fs.ts:80` `chownFreshTree`).
- The loader gives away ownership under strict guards: `chownFreshTree` refuses any tree it did not just create and never follows symlinks (post-order `lchown`); an existing tree on the volume is never traversed. Writes that matter are `writeFileAtomic` (`fs.ts:132` temp + rename). `createDirIfMissing` (`fs.ts:34,117`) never touches an existing path.
- Build: `repo.ts buildIfNeeded` runs `npm ci && npm run build` as uid 1000 (when privileged) with a time bound (`repo.ts:266` `buildTimeoutMs`, `:271` `npm ci`), then verifies **only that `lifemodelEntry` exists** (`:284`), and records the commit in root-only `state.json` (`:289`). There is no hash, signature or immutability of the entry file: `repo/` is uid-1000-writable, so the instance can rewrite the code the next start executes (stated in `egress.ts:13`: "it may rewrite its own code").
- `safe.directory` is named per exact path, never `*` (`repo.ts` `gitArgs`).

### A3. Network authority (loader/src/egress.ts, config.ts)
- A root-installed iptables/ip6tables owner rule (`loader/src/egress.ts:36` chain `LIFEMODEL_EGRESS`, flushed+refilled per install, idempotent) confines **exactly `config.lifemodel.uid`** (`:109-110`): allow the named loopback services (Agent Vault mitm/`HTTPS_PROXY` port 14322 — `agent-vault.ts:229` `--mitm-port`, loader HTTP 7000, embedded resolver's DNS port, protocol+port bound), `ESTABLISHED,RELATED` replies (`egress.ts:20`), `REJECT` (not DROP; `:60`) everything else from that uid. All other uids, root included, are untouched (`egress.ts:27`) — the rule names the one uid it confines.
- Install requires the image's `iptables` and `--cap-add NET_ADMIN` (`egress.ts:68` `EGRESS_CAPABILITY`); either missing is a fatal one-line exit before lifemodel starts. IPv6 is covered when `/proc/net/if_inet6` shows addresses.
- The container default network is Docker's bridge; the egress rule is the inner boundary. Outside the container (the host `docker run` documented in `README.md:192-200`) only `--restart`, `--stop-timeout 120`, `--cap-add NET_ADMIN`, volume and port publishing appear — **no `--network`, no bandwidth/policy flags**.
- The vault proxy is **not strict-deny** ("a host with a service gets its credential attached… any other host passes through the proxy unchanged" — README). Private ranges are blocked by the vault's netguard (with an owner overridable env `AGENT_VAULT_ALLOW_PRIVATE_RANGES`).

### A4. Credential authority (loader/src/agent-vault.ts, env-boundary.ts)
- Named-secret denial: the child's env is rebuilt in `env-boundary.lifemodelEnvironment()` — an explicit name allowlist (`env-boundary.ts:27`), the vault-built proxy environment appended over it, and a strip list (`:75`: `OPENROUTER_API_KEY`, `AGENT_VAULT_MASTER_PASSWORD`) removed by name regardless of how they arrived. This proves "no model key / no vault admin credential in the process" — nothing more.
- The vault store is root-only `0700` (`agent-vault.ts:56` STORE_MODE; passwordless; protection is the directory permission, decision 4); `vault-ca.pem` `0644` readable-not-writable by uid 1000; runtime `vault-owner.json` and `vault-proxy.json` under the volume’s loader directory `0600` root. One vault agent (`lifemodel`, role proxy) owns the single proxy credential (`agent-vault.ts:477,534`); the loader's build is given the same proxy environment. The proxy credential IS a credential in its own right: the agent token rides in the proxy URL (`agent-vault.ts:750-760`).
- The egress rule deliberately permits the credential proxy (port 14322, `agent-vault.ts:229`) for uid 1000 — the network allowlist and the credential boundary share one uid identity, and what the mitm port grants a credential-less process is Agent Vault's own (external) behavior, not verifiable from this repo.

### A5. Resource ceilings
- For the **instance container itself**: none in the repository and none in the documented run command. Deployment-only comparison points inside the repo: Motor Cortex skill containers default `--memory 512m --cpus 1.0 --pids-limit 64` with `--read-only --cap-drop ALL --security-opt no-new-privileges` and `--network none`/bridge+egress-proxy (`src/runtime/container/types.ts:298` `DEFAULT_MEMORY_LIMIT`, `:301` `DEFAULT_CPU_LIMIT`, `:304` `DEFAULT_PIDS_LIMIT`, `container-manager.ts` `docker create` security flags; detached browser containers `1g`/`512` pids); the disposable test boundary runs `--cpus 2 --memory 3g --memory-swap 3g --pids-limit 256` (`scripts/test-isolated.mjs` `LIMITS`). These implement **whole-container** caps for *different* containers; they are not per-process and not per-candidate.
- **No rlimit/ulimit/cgroup/nice primitive exists anywhere in the loader or in lifemodel's own start path** (grep over `loader/src` and `src`: zero hits). `exec.ts spawn` passes cwd/env/uid/gid/timeout only (`loader/src/exec.ts:95`).
- Recorded-not-verified environment claims (tracker `lifemodel-653` task body, a prior investigation's statements the tracker carries — unprivileged namespaces blocked in a default container, Landlock ABI 7 available, cgroup filesystem read-only): this report did **not** and cannot re-verify them by source reading alone; they are carried as a *record* requiring named proof or acceptance before any design leans on them. Landlock itself is a **filesystem** ACL family: even fully available, it bounds file access, not CPU, memory or pids.
- The task-executor design (653) lists per-task uid, Landlock files, an iptables owner rule to Agent Vault with injected keys, rlimits and loader-side ceilings, but **none of its enforcement is implemented today** (`lifemodel-653` open), and its rlimits are per-process knobs (seconds of CPU, address space, per-uid child counts), not the aggregate per-candidate caps (wall-time budget, whole-process-group RSS, candidate pids) that the generation contract actually needs.

### A6. What the lifemodel process does by itself (candidate activation reality) — code-order observations; their interpretation as admission guarantees is uniformly a cooperative-seam reading, with the exhaustive audit assigned to `lifemodel-b0r.3.2` (constructor plugin/provider loading is not audited here for network or side effects)
- `src/index.ts main()` does construction then, in this order: starts the settings interface (`index.ts:45`, settings server, fixed port 7100, before the loop), then `void telegramChannel.start()` (`:79`, unawaited), then `coreLoop.start()` (`:83`).
- `createContainerAsync` (construction) already: starts deferred auto-flush (`container.ts:515`, 30 s interval), loads the plugin loader (each plugin gets a scheduler primitive), loads state, restores the user model, creates the vector store (LanceDB owns its own files — `lance-vector-store.ts:8` — and the class has **no close method**, verified absence), registers Motor Cortex, **replays durable inbound entries into the loop's queue** (`container.ts:1157`), flushes storage once (`:1193`), registers state components, and starts state auto-save (`:1205` `startAutoSave`).
- `shutdownSequence` (`src/core/container.ts:301-351`) is the one ordered release: intake stop → loop drain → state/registry flush → channel stop → `closeDurableWrites()` (`:348`) + storage shutdown last. It is bounded best effort. Verified absences only (not a blanket impossibility claim): no current API re-opens a live graph after `shutdownSequence` (no component re-wires), `LanceVectorStore` exposes no close method (`src/storage/lance-vector-store.ts:1-9` header and the class surface), the deferred/JSON stores shut down rather than pause (`container.ts:348-350`), and the registries/memory handles handed to cognition have no release and rebuild contract. Whether a same-process rebuild REQUIRES open handles or can be staged fresh is unproven either way — it is `lifemodel-b0r.3.2`'s question.

## C. Explicit unknowns / gaps (named, not resolved here)

1. Whether the vault's mitm listener grants anything to a credential-less process — external Source (Agent Vault), not pinned/reviewable in this repo — so credential-removal as no-external-activity is UNKNOWN here (see credential row).
2. Whether a candidate may share the primary's Agent Vault token (credential admission is token-scoped today) — owner decision; OR the alternative second-agent slice.
3. Same-uid signal rights: candidate could kill/stop the primary (POSIX same-uid). An enforcing process-authority boundary is required; accepting this risk does not satisfy containment or continued primary service. UID separation would also require the filesystem/network/credential policies above.
4. Per-candidate CPU/memory/pids ceilings: no mechanism inside the current image, and the per-process rlimit family cannot express aggregate caps (see ceilings row). Any chosen mechanism is a new primitive requiring approval. The 653 environment claims (cgroup fs read-only, namespaces blocked, Landlock ABI 7) are recorded-not-verified and carry no weight until accepted.
5. A different-uid candidate needs: chain entries for its uid (egress), ownership re-grant for shared data at activation (reverse of the current one-time `chownFreshTree` handover), and either no proxy env or a second agent token.
6. Read-only view of the live store for a candidate: mode-bit layout does not exist today for `data/` (same-uid sharing is currently all-or-nothing).
7. Generation identity verification at spawn (hash vs recorded build identity): none; both the computation and the comparison are implementation slices.
8. Inbound replay and plugin/provider/scheduler creation occur at construction; what "candidate initialized but powerless" can mean is only the cooperative boot-start seam until 3.2 audits every constructor action for side effects (network calls at plugin/provider load are unaudited by this report). Which constructor actions a rehearsal may run is 3.2's decision, not proven here.
9. Whether the durable graph can be re-opened same-process is NOT settled by a blanket claim; what is verified is the absence list below, and the modal question (is it enough?) is 3.2's.
10. Heavy-CI expansion remains explicitly blocked (PR23 C07 and the PR-only ci-image exception carry the boundary; unchanged by this report).
11. No second durable "candidate panic / attempt" record exists beside `panic.json` (`state.ts:24-44` names the four files); restart-safety for attempts is a design obligation, not present behavior.

## D. Recommended bounded, source-supported next slices (for b0r.3.3 to reconcile; nothing authorized to implement)

1. **Sealed-generation directory contract (source design only).** Distinguish staging (where the build writes; uid- or root-staged) from the sealed publication (root-owned tree never handed to the child, uid read-only entry via mode bits, hash-recorded identity re-checked at spawn — `repo.ts`/`fs.ts`/`state.ts` name where state lives; the publication path itself does not exist today). Names the R01 verification point without changing any constant and without presenting `chownFreshTree` as the seal.
2. **Candidate admission contract in the supervisor (source design only).** A second, sibling slot beside the single child; per-change spawn inputs limited to cwd/env/uid/gid/entry the supervisor already accepts; the boot-start seam stated as cooperative only — "main() is where the starts live" is an observed code seam, not a no-external-activity proof, and the exhaustive constructor/plugin/provider admission audit is `lifemodel-b0r.3.2`'s pending work. Records the same-uid vs other-uid fork with its network/ownership consequences — the exact decision 3.2 must take.
3. **Ceiling-mechanism decision memo (owner-facing).** State plainly that no current primitive implements per-candidate ceilings. Rlimits alone and whole-container-only caps are inadequate and are not acceptance alternatives. Identify an enforcing aggregate candidate mechanism before choosing numerical ceilings or authorizing launch. Note that even Landlock availability rests on a recorded-not-verified claim. No constant or mechanism is chosen.
4. **Credential admission slice note.** Either the shared-token acceptance (stated openly, like today's build) or a second vault agent provisioning route in the loader; Agent Vault's own API is described as still changing (Dockerfile pin comment), so the loader-side provisioning change must ride one pinned version.
5. **Storage handover feasibility stays owned by b0r.3.2** — with `lifemodel-ww8`'s pending owner exception and 653 as a task-executor precedent (its enforcement unimplemented and its environment claims recorded-not-verified). This report claims no ownership there and asserts only the verified absences, so neither same-process rebuild nor its impossibility is presumed.
