# Independent source-only design review — lifemodel-b0r.8

**Verdict: blocking corrections required before reconciliation.** This is a review of the two raw `/tmp/lifemodel-b0r-{authority,handoff}-options.md` reports against the accepted `docs/features/instance/generations-design.md` (R01–R09), feasibility and containment/lifecycle reports, and loader/app source in the `b0r-design` tree at 78a5dca. It is not a runtime test, implementation acceptance, or proof of platform/native behavior. I read `AGENTS.md` and `docs/backlog-integration.md`; I made no product, tracker, dependency, or CI changes.

## Blocking authority / budget findings

1. **Watchdog is not a hard per-candidate aggregate ceiling.** Authority §§4C, 5, 6, 7 proposes `/proc` UID RSS/CPU/pid sampling, killing after a sampled breach, and recommends A+C staged launch. A 10x fork or memory burst can exceed the limit or starve/kill the primary before the next sample; CPU accounting is retrospective; RSS neither caps allocation nor represents cgroup memory usage. A missed sample, blocked loader, or PID churn makes the asserted bounded overshoot and “no failure mode loses primary” unsupported. R02's enforced containment and feasibility's per-candidate aggregate ceiling/primary-continuity gate require a *proven preventive aggregate kernel mechanism before candidate launch*, with owner-specified limits. The watchdog can be defense-in-depth/diagnostics, never the acceptance mechanism. `loader/src/exec.ts` exposes no aggregate limiter; README's instance run flags provide none. The cgroup subtree in this deployment is recorded-not-verified; availability and real process-tree inheritance must be proved rather than assumed. Whole-container caps and per-process rlimits do not replace this gate.

2. **Owner risk acceptance is not enforcement.** Authority §5 says cgroup proof *or owner acceptance* before launch; §§7–9 leave watchdog as a usable fallback. Delete acceptance-as-proof and any A+C launch path. Failure to secure a usable aggregate limiter means no overlapping candidate in this design, not approval of a weaker candidate. The cheapest staged order is enforce/verify candidate identity, immutable code, ingress/egress/proxy and aggregate ceilings first; only then rehearse; no numeric ceilings or thresholds were selected in this review.

3. **“Spawn-fixed credentials” is too broad and misses inherited powers.** Authority §3 claims UID/GID/groups cannot change post-spawn and option A says a different UID denies signals. A candidate can have effective/saved IDs, supplementary groups, capabilities, setuid executables, or inherited descriptors; a UID distinction alone is insufficient without proof that it cannot regain the primary's identity or signal privilege and cannot use inherited live-store/socket handles. Verify credential vectors, no-new-privileges/capability bounding, exec/setuid surface and file-descriptor inheritance at spawn and after activation. Node `loader/src/supervisor.ts:165-174` specifies only uid/gid for privileged spawn; it does not prove all those restrictions. Similarly an environment variable is not an enforceable authority: a child can alter its own environment; authenticated loader grants must not trust it.

4. **Network/door grant must cover already-open paths.** `loader/src/egress.ts` uses UID-keyed owner rules, but permitting network ports at activation is not sufficient if rehearsal inherited an allowed socket/FD, a pre-established connection survives a rule change, or a proxy already accepted a token/connection. The pinned Agent Vault 0.40.0 binary's authorization behavior is not source-proven here. Deny/revoke existing descriptors and flows, prove proxy authorization separately, and ensure activation opens new powers only for the fenced attempt; `ESTABLISHED,RELATED` treatment must be reviewed. Evidence for immutable generation identity also needs seal/hash verification at execution, not merely an entry-file existence check (`loader/src/repo.ts:255-291`).

## Blocking native handoff / publication findings

5. **Package API declarations are not native release proof.** Handoff §2's pinned declarations identify LanceDB Table/Connection `close()` and Transformers pipeline `dispose()` as available; no pinned native fd/mmap/worker completion follows from `void`, a wrapper's `isOpen()`, or an awaited JS disposal. Connection closure does not close independent tables. `src/core/container.ts:301-352` currently shuts down the app but does not close every vector/table/pipeline/logger/worker, plugin, Motor, settings or async continuation. Name a complete consumer/descendant/external-writer inventory and verified closure/gate evidence before a second opener; lack of proof refuses activation. Package claims were read from the raw report, whose stated evidence was npm tarballs pinned by lockfile; this reviewer did **not** independently download or execute tarballs/native modules, so treats declaration claims as source-report evidence only, not release verification.

6. **Child intent cannot certify the last flush.** Handoff §4.2 P-1 puts an intent/step marker before `storage.shutdown()`, but `src/core/container.ts:341-351` deliberately places storage flush last. The child cannot authoritatively attest completion before it happened, nor may a child-written marker grant itself permission. A loader-owned fenced record may capture intent; a final authenticated post-flush stop report plus loader-observed process/native/descendant/external-owner release must establish completion. If such evidence cannot be obtained without exiting the primary, declare the gate unsatisfied, not “verified”. `loader/src/supervisor.ts:177-204` observes process exit/exit code, not each app-side flush or native owner.

7. **Current loader `writeFileAtomic` is not crash/power durability.** Handoff §§4.1, 5.1, 6 equates `loader/src/state.ts:182-189`'s atomic write and pointer flip with a durable record. `loader/src/fs.ts:132-138` implements writeFile → rename → chmod, without file or parent-directory sync. Neither its previous `builtCommit` use nor `src/storage/json-storage.ts:269-293` (temp handle sync, rename without parent-directory sync) proves cross-file persistence on crash/power failure. The proposed design requires explicit file sync, stage-tree sync and containing-directory sync, ordered staging before authoritative pointer record, atomic rename, and recovery validation; if the filesystem/platform cannot deliver the stated guarantee, mark the scenario unproved. An atomic name switch is not a durable transaction by itself.

8. **Spawn-time root pointer conflicts with same *running* candidate.** Handoff §5.1 says the loader's per-child `DATA_PATH` spawn option makes every consumer ride the published root. `loader/src/supervisor.ts:165-169` sets env only for a new spawn; `src/index.ts:24-39` constructs once, and `src/config/config-loader.ts:20-23` reads a process env default. The fixed owner premise rejects N2 fresh-process replacement. A fenced authenticated activation message must convey the authoritative latest root into the existing candidate, after private-graph release, and the SAME process must freshly build all consumers against that path before live admission. Audit every storage/config/vector/models/plugins/settings/registry/logging path and construction side effect; cannot claim all consumers use `DATA_PATH` from inspecting config alone. N2 may be documented as rejected context, not a pending owner choice.

9. **Zero-writer window and migration executor remain unproved.** Handoff §5 asserts exact zero writers and full persisted cross-store consistency from `shutdownSequence` plus a marker. Today's settings writer, LanceDB native files, dynamic plugins, scheduler promises, log worker threads, Motor descendants and post-shutdown deferred-write behavior require owner-specific gating and terminal verification. Assign a trusted migration executor and path credentials in the post-primary/pre-candidate gap, prove it never races surviving owners, enumerate all data and config roots/format versions, verify quiesced copy *and* migrated copy before publication, and specify how stage failure cleans without altering latest authority. File-set/mtime checks or a loader ledger in §6 do not prove absence of writes or short racing windows.

10. **After publication, latest root stays authoritative on activation failure.** Handoff S-5 says fallback uses CURRENT data, but §5's prepublication failure rule and S-6 “primary remains/becomes authority again” are ambiguous when `published` already happened. A post-publication failure cannot select the retained pre-migration root, even if old primary code is chosen. Record recovery phase semantics: the published root is current; old-generation fallback must run its owned down-migration against that latest root in a separately verified quiescent window, with a new durable publication and refusal/maintenance if impossible. Never resurrect historical data over postpublication writes.

## Worked trade/verification gaps to carry into the integrated design

- Remove the pseudo-trade between N1 same initialized process and N2 process exit: owner direction already fixes N1. The genuine trade is whether N1's native and all-consumer close/rebuild can be proved; if not, fail the feature gate and seek an explicit owner change separately.
- A generation data-root pointer is a plausible single publication authority, but handoff §5 must establish same-process activation, trusted migration executor, actual durability primitive, format-ownership and verified all-writer exclusion before describing it as meeting R08. Disk doubling and 10x copy latency need explicit disk budget/refusal and bounded handoff policy; no constants invented here.
- Option A's identity, seal, egress and live-data ACL/group model must specify activation grants/revocation and rollback for fresh same-process construction, including paths newly created by LanceDB. `lifemodel-ww8` remains an open owner item and `lifemodel-653` retains task-executor containment ownership; do not transfer their decisions silently.
- R04/R06 recovery table must distinguish crash points before/after each *durable* publication, stop/panic epoch invalidation and exit-75 same-generation restart, and classify failures from completed internal work per R05 rather than PID/HTTP/tick. On uncertainty refuse or enter maintenance rather than claim a safe fallback by reading only an exit code.
- Proposed checks must test attempted unauthorized writes/signals/egress, retained FDs/flows, 10x bursts and process-tree churn under actual preventive limits, native handle lifetime, stage/record sync crash points, current-root postpublication rollback, and actual completion-based health. These are later execution/acceptance gates, **not run** here. Heavy first-start image acceptance stays CI-only per AGENTS.md.

## Targeted disposition on corrected retained contracts (78a5dca; source-only)

Reviewed `docs/features/instance/generations-authority-options.md` and `docs/features/instance/generations-handoff-options.md` against findings 1–10 above. **All listed design-text blockers are addressed as explicit conditional proof gates or rejected alternatives; no residual correction to these two concise contracts is blocking this source-only design reconciliation. This does not accept implementation or environmental/native capability.**

- Findings 1–2: authority options reject watchdog, A+C launch and owner acceptance in place of a preventive kernel-enforced per-candidate aggregate ceiling. Delegated cgroup availability, isolation, numerical limits and primary reservation remain unproved gates; no launch today.
- Findings 3–4: credential variants, capabilities, supplementary groups, setuid/exec escape, inherited descriptors/connections/mappings and broker auth are required proofs; mutable child environment is explicitly non-authoritative. No claim that a distinct UID alone settles them.
- Findings 5–6: pinned declaration limits, independent table closure and native/worker/descendant uncertainty are named. Child preflush intent is diagnostic only; loader-owned fenced record and validated final release are required, uncertainty refuses.
- Finding 7: current write→rename→chmod helper is acknowledged non-fsync; staged-file/dir and record-file/parent sync ordering, failure outcomes and platform verification remain required before durability claims.
- Findings 8–9: settled same-process requirement and rejected process replacement are explicit. Authenticated root/config payload plus whole fresh in-process construction and all-consumer path audit replace spawn-only `DATA_PATH`. Unknown writer/reader/continuation and unproved migration executor isolation refuse; 10x staging capacity and bounds are gates, not assumed.
- Finding 10: after publication the newly published root remains latest authority; fallback transforms that root, never old retained roots. Prepublication and postpublication failures have different authority outcomes.

**Remaining work is proof/implementation, not a missing correction to these targeted source-only design statements.** Pinned-package claims are sourced to the raw worker's public-tarball reading, not independently validated here; neither report says JS declarations prove native close. `lifemodel-653`/`lifemodel-ww8` ownership, deployment approval, ceilings and health constants remain open; no probes or acceptance performed in this disposition.
