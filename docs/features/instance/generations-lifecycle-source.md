## 1. Answer to the task question in one paragraph

At PROCESS level there is exactly one owner: the loader's supervisor (`loader/src/supervisor.ts`) owns ONE child process, and the child's lifecycle is `createContainerAsync()` (init + restore, src/core/container.ts:477-1226) followed by `main()` in src/index.ts (settings server, channel start, loop start). Within the child MANY component owners exist with their own init/release paths (the loop, DeferredStorage, channels, plugins, Motor Cortex, loggers, settings server), §2-§6 map them; ownership is per process at the top and per component below. There is NO inactive initialization path and NO reusable graph-release API in this code: `createContainerAsync` is itself active (it starts auto-flush, activates plugins — plugins write schedules into shared storage — and recovers Motor Cortex runs, including launching Docker containers and pruning artifacts by age), and the only release surface is `shutdownSequence` (container.ts:273-353), which is bounded, best-effort, and expresses its verdict only through the process exit code (graceful 0/75; hard exit 1 at the deadline, src/core/hard-exit.ts). "Unknown release refuses activation" has no mechanism today: a starting child cannot know whether a previous owner released, and nothing in the child reads a generation/epoch marker at startup. The only cross-process admission primitives that exist are the panic file (`loader/src/state.ts:152`), the exit-code-75 contract (`src/settings/restart.ts:16`, `loader/src/supervisor.ts:46`), the inbound log's per-recipient offsets with its bounded dedup ring, and per-file atomic renames in JSONStorage.

## 2. The actual process lifecycle (launch, activity, stop), as the loader owns it

- One child per loader. `loader/src/supervisor.ts` start-once (`startOnce`, supervisor.ts:263ff); states `stopped|starting|running|stopping|failed`. The spawn verdict ("the OS really started this") is an awaited event (`onSpawn`, loader/src/exec.ts:80) because spawn failures arrive asynchronously.
- Launch is `node <entry>` with an EXPLICIT env (env boundary list, loader/src/env-boundary.ts:27-75; secrets stripped by name, :75), `DATA_PATH`/`HOME` set from the volume (supervisor.ts:152-157), and — when privileged — `uid/gid` (`spawnOptions`, supervisor.ts:168-172). No distinct filesystem or namespace: same image tree, same kernel identity. lifemodel-653 records the owner direction: same-UID separation is NOT isolation.
- Egress: ONE iptables owner rule keyed on the uid, installed as root BEFORE lifemodel starts (loader/src/egress.ts; its chain is flushed and refilled at each install). It confines uid 1000 to the named loopback services and the vault proxy. A candidate reusing this uid shares that rule by construction; a second process is NOT less able to egress.
- Restart semantics: only exit 75 is a request (`restartRequested`, supervisor.ts:219-229 — no backoff, not counted as failure); other exits get backoff reset by a run past `healthyRunMs` (:229-247); the panic file blocks starts (:288-298); stops bump an in-memory `epoch` that drops scheduled restarts (:394).
- Loader stop is ONE budget (`stopBudgetMs`, loader/src/app.ts:307-311): own server close, then `supervisor.stop` (SIGTERM, drain bounded by `drainWaitMs` − kill room, then SIGKILL and reap wait; supervisor.ts:433-475 — `stopped/pending/drainTimedOut` verdicts are RETURN VALUES), then Agent Vault stop (app.ts:332), then Caddy (app.ts:336), then a second reach over anything a fenced startup created between steps (`stopStartupLeftovers`, app.ts:139-179).
- The child's stop begins on SIGINT/SIGTERM/uncaughtException/unhandledRejection (src/index.ts:260-275), routed into ONE coordination `runStopSequence` (src/index.ts:198-228): the hard-exit timer is armed FIRST (before even the settings close, src/index.ts:206-216, hard-exit.ts: the timer is REFERENCED until disarmed), the settings server is closed bounded (grace 5 s, settings/server.ts:100; still-arriving saves are aborted at their publication point via the stop signal, server.ts:383), then `await active.shutdown()` (src/index.ts:224), then `process.exit(code)` — 0, 1 on error, 75 for a settings save (src/index.ts:164, restart.ts:16).

### What "release" is today, exactly
`shutdownSequence` (container.ts:273-353), awaited step by step, with ONE overall `deadline = Date.now() + coreLoop.getStopDrainTimeoutMs()` (container.ts:1213-1225). Deadlines are enforced ONLY inside the loop drain: the tick/scheduler-callback/turn/sends waits use `awaitWithinDeadline` against that deadline (core-loop.ts:913-938); every LATER step — the state/registry flushes (step 3), the channel stops (step 4), and the final `storage.shutdown()` (step 5) — has NO internal bound; only the separately armed hard-exit timer covers them (src/index.ts:198-227). The container's ShutdownSequenceDeps comment says "each wait inside is bounded by it" (container.ts:227-235) — the CODE bounds only the loop-drain waits; the comment overstates.
1. `intake_stop` — `channel.stopIntake()` (Telegram: `bot.stop()` plus a bounded 5 s drain of in-flight emit handlers, telegram.ts:136 and :311-338) or `stop()` (container.ts:309-318).
2. `loop_drain` — `coreLoop.stop(deadline)` (core-loop.ts:887-945): await in-flight tick (`awaitWithinDeadline`, :913-920), scheduler tick (:921-929), the COGNITION turn (`drainPendingCognition`, :934; an overrunning turn is abandoned and its entries replay via the inbound log), awaited sends (`awaitPendingSends`, :938 with 961-970: remaining sends are logged-and-released, the channels stop anyway). Late intents fenced (`lateEffectsFenced = true`, :942; guard :1039).
3. `state_flush` — `stateManager.shutdown()` (auto-save cleared, final save, state-manager.ts:238-247), `recipientRegistry.flush()` (debounced save, recipient-registry.ts:422), `ackRegistry.flush()` (container.ts:327-331).
4. `channel_stop` — full channel `stop()` (sending refuses afterwards; Telegram nulls bot and download client, telegram.ts:349-358).
5. `storage_flush` — `coreLoop.closeDurableWrites()` FIRST (core-loop.ts:993-995; enforced at settleTurn, :698-716: a late commit is dropped, its entries stay on disk for one replay), then `await deps.storage.shutdown()` (deferred-storage.ts:296-317: timer cleared, awaited settle loop until `getDirtyCount() === 0`, guard 100 throws on a stuck flush). If it throws, the stop sequence rejects, the shutdown memo clears (container.ts:361-372), the hard-exit timer is STILL ARMED, and the process leaves with code 1 at the deadline.

Verdicts this machinery can express: `stopProgress().step` ('done' on the container, container.ts:1212) and `coreLoop.stopReport()` (core-loop.ts:1002-1010) — but only in the memory/log of the dying process. There is NO durable release record anywhere in the source: an exit code is an outcome an outside watcher can observe (the loader sees it, supervisor.ts settle), not a trace the process writes, keep, or re-reads.

## 4. Restore/replay contract (what a start inherits from shared data)

- Inbound log: `replayable()` = entries whose turn recorded no outcome (per-recipient offsets, bounded recentKeys ring, inbound-log.ts:340-360 and :65). Replay (container.ts:1157-1186): the registry route is re-created deterministically (:1162-1164); an incomplete photo receipt is re-fetched over the network (:1173-1178) or queued as caption text; surviving entries are queued (`pushSignal`, :1179). Entries STAY in the log until a turn records an outcome (removal paths: settled turn, core-loop.ts:698ff).
- Internal signals, queued schedules, Motor Cortex results and reactions are NOT durable; a stop loses them (container.ts:1188-1192 comment; core-loop.ts:880-885).
- Schedules persist per plugin through the storage path (scheduler-primitive.ts:691-693) and fire as soon as seen (`nextFireAt <= now`, :256/:331) — restart-safe by the repo's design principles.
- Motor runs persist as ONE object under the `motor-runs` key through DeferredStorage with explicit flush per transition (motor-state.ts:14-66). Recovery per status is motor-cortex.ts:1545-1731. In-flight Motor containers at a stop are NOT a shutdown step: they are abandoned by deadline, then either reaped dead at the next start's prune — or pruned alive if older than 5 minutes (see 7, conflict 1).

## 5. Release questions answered against source (awaited vs absent seams)

1. **Awaited release that exists:** the five-step sequence is awaited in order; ONLY its loop-drain waits are individually deadline-bounded (`awaitWithinDeadline`, core-loop.ts:913-938); steps 3-5 carry no internal bound and fall to the overall hard-exit timer (src/index.ts:198-227). The settings save aborts at publication point; late commits are fenced by `durableWritesClosed`; `DeferredStorage.shutdown` throws on a flush that never settles — the stop then rejects, the hard exit stays armed, and the process leaves at the budget with code 1. Note what a completed stop does NOT prove: exit 0/75 is the OUTSIDE-OBSERVED tail of the process, never a complete-release proof — sends that never drained are logged and the channels released anyway (core-loop.ts:961-970), an overrunning turn's entries replay rather than commit, and all holders outside the deferred layer (§5.2) are simply not part of the observed sequence. "Release complete" is not a state this source records, and exceptions before the final drain also produce no verdict beyond the exit code an observer sees.
2. **Known-NOT-awaited (absent seams):** (a) pino file transports — worker threads that cannot be fenced/awaited (named in source, container.ts:107-113); (b) LanceDB — the wrapper has NO close/dispose (method set: search/count/save/delete/getById/getAll/clear/persist/bulkImport, lance-vector-store.ts) and `Connection`/`Table` handles live for the process life; (c) the embedder's ONNX session — lazily created, never released; (d) Motor Cortex Docker containers of runs in flight — neither a stop step nor reliably released; next start prunes anything older than 5 min whether alive or not; (e) `egressProxyManager` module singleton state (per process); (f) plugin `deactivate()` is never called at process stop (only via the runtime unload tool, plugin-loader.ts unload path); built-in scheduled activity routes through the loop's scheduler tick (core-loop.ts:1270-1274), which the stop awaits. This is not a timer guarantee for arbitrary dynamic plugins, whose import/activation can own timers outside the loop; §3b therefore denies/defers their admission until verified restriction or exclusive release.
3. **Unknown release refusal impossible today, on this shape:** the sequence itself does not check the deadline between steps; its implementation is the loop of awaited steps (container.ts:301-353) with `awaitWithinDeadline` resolving past the deadline (core-loop.ts:913-929), and container.ts:294-297 documents that continuation — the DEADLINE is enforced by the SEPARATE armed timer (src/index.ts:198-205, hard-exit.ts:66-78: `process.exit(1)` at the budget, `STOP_DEADLINE_EXIT_CODE`, hard-exit.ts:47), which is only absent when the module is not the process owning the stop. A stop that completes BEFORE the budget disarms the timer and exits with its own code (src/index.ts:223-227); a stop that reaches the budget while unfinished leaves with code 1 and its pending step named in one line (hard-exit.ts:55-78). The timer is the deadline's only enforcement, and nothing after it reports — an "uncertain release" is not carried anywhere, and NO code path exists today that sets a durable marker, reads one at start, or refuses a start on it.

## 7. Two-actor risks on one data root — source-supported risks, CONDITIONAL on a same-store simultaneous activation (not measured events)

The conflicts below are consequences the source supports if a second container is constructed against the shared root while the primary still runs; they are not illnesses of today's single-instance runs, and a working admission barrier (exclusive store ownership) prevents them rather than curing code that is wrong anyway:
1. Motor Cortex: the candidate's `prune(5 min)` CAN `docker rm -f` the primary's live Motor Cortex container (age > 5 min; the labels carry no generation/owner distinction, container-manager.ts prune), and both processes WOULD resume the same `motor-runs` record (recoverOnRestart hands the record to `runLoopInBackground` unconditionally at the resume site, motor-cortex.ts cited above; container creation itself additionally requires `isDockerAvailable()`, and a Docker-less candidate's Motor attempt still advances run state through `runMotorLoop`/storage). Gated on the same data root and an active `motor-runs` record; on Docker availability; NOT observed to fire in this repository — a risk with conditions, not an event.
2. Storage: both run `storage.startAutoFlush()` (30 s) and `stateManager.startAutoSave()` (2 min); both flush → both atomic-rename the SAME files. Last rename per file wins — recency-based, per key, not transactional.
3. Plugins: both `activate()` → both `persistSchedules()` for the same schedule ids; each candidate's write races the primary's latest write.
4. Inbound log: two SIMULTANEOUS readers of the same `core/inbound_log.json` would BOTH queue the same uncommitted entries (both call `replayable()`; containers.ts:1157-1186), and BOTH may answer them. The bounded recentKeys ring and the compaction-surviving dedup horizon are a DOCUMENTED DELIBERATE contract (inbound-log.ts:28-41 — owner decisions, comments 49/54; per-recipient offsets are the once-only guarantee for one process), NOT a defect; the risk here is the second reader, i.e. concurrency over one log, which exclusive admission removes.
5. Settings: port 7100 bind fails on the candidate (non-fatal by code, src/index.ts:100-113) — the candidate would have NO settings interface; the loader's ports are where a control interface must attach (B0R-R09 should build there).
6. Telegram: two bot clients with one token; grammY conflict behavior for polling is UNKNOWN from source (no probe allowed).

## 8. Inactive-candidate admission contract, as the source can support it

- Without refactoring, constructing against live stores already runs the effects in §3. Omitting the loop/channel/settings starts is only a cooperative seam, not inactive initialization. Loop start/stop guards do not establish full-container reuse; the shutdown lifetime is described below.
- Rehearsal graph rebuild: `JsonGraphStore`'s data is ONE storage key (`graph`, graph-store.ts:463-470), so dropping the in-memory store and reloading from storage is a plain JSON reload — safe only AFTER release is verified, because the rebuilt store instance must be wired into consumers built at construction (`JsonMemoryProvider` holds vectorStore+graphStore, container.ts:674; `memoryConsolidator` and the cognition tool registry hold their references) and there is no swap-in surface. LanceDB rebuild is not supported by THIS wrapper while another handle is open (no close/dispose; one `Connection` per instance, lance-vector-store.ts:130-132); the pinned native package's API surface is unverified in this report, so the honest phrasing is: no supported reopen/rebuild path exists in `30b9627`, and same-process rebuild obligation carries the release-verification and consumer-rewiring requirements the planning decision already state.
- LanceDB handle release: covered in the roadmap above — the wrapper has no close (§5.2), the pinned native API is unverified here, and any vector-side rebuild presupposes handle release plus consumer rewiring; nothing in `30b9627` supports a hot replacement of an open LanceDB store.
- Restartability nuance: `coreLoop.start()` after `stop()` is guarded-safe (core-loop.ts:853-877 resets `durableWritesClosed`, `lateEffectsFenced`), but the CONTAINER has no supported restart surface after `shutdown()`: `DeferredStorage.shutdown` cleared the cache and stopped the flush timer (deferred-storage.ts:296-317), state auto-save timer is cleared (state-manager.ts:238-247), and nothing re-arms either — a restarted loop would defer writes behind a timer that is off.
